# 金睛鉴诈面试速读与讲解手册

> 适用场景：面试前快速熟悉仓库，并能诚实、连贯地介绍项目。内容按当前仓库代码和阶段报告整理。涉及“我负责什么”的说法，请只保留与你实际经历相符的部分。

## 今晚优先记住的五件事

1. **项目是什么：** 基于已有竞赛源码做的本地化反诈调查原型。新增主展示入口是 Python/Flask 本地工作台，地址 `127.0.0.1:5050`。
2. **核心流程：** 文本或媒体进入本地处理，生成脱敏线索和 `evidence_id`；规则先给风险提示，RAG 提供已复核资料；一个有限预算的 Agent 按观察选择白名单动作，必要时检索本机相似视频或建立人工复核工单，最终生成带来源和不确定性的案件报告。
3. **为什么用 Agent：** 前处理步骤明确，普通代码更可靠；后续核验路径会随 URL、检索、媒体观察变化。Agent 的作用是“看当前状态—选下一步—执行—读回执—再规划”，不是把所有代码都换成 LLM。
4. **业务工具：** Agent 可提供分场景止损建议、整理联系银行/报警前要准备的信息、检索本机历史视频候选、创建人工复核工单；另有时间线、缺口和证据编号工具。总计 11 个可选动作，每轮最多 8 次调用。URL 外部扫描需用户单独确认。
5. **记忆是什么：** LangGraph 的 SQLite Checkpoint 保存单个案件的调查状态和短期上下文；它不是跨案件的用户长期记忆。Web 异步 Job 状态仍在进程内存，重启会丢。
6. **最大限制：** 知识卡目前只有 5 条；媒体伪造分数未校准；6 个动作场景只是研发烟测；没有证明识诈准确率提升，也没有证明 Agent 优于同预算固定流程。

## 30 秒版本

> 金睛鉴诈是一个基于既有反诈项目源码做的本地多模态调查原型。我主要介绍新增的 Python 调查工作台：它把截图 OCR、音视频线索、隐私替换和高危规则先做成有编号的证据，再用可追溯 RAG 查相关资料。对于信息还不完整、下一步取决于新发现的案件，LangGraph 中的单 Agent 可以在有限预算内选择知识检索、离线网址检查或媒体信号复核；结果作为观察回到规划环，必要时暂停向用户补问。当前重点是调查过程可见、失败能收敛和证据可复查，尚未证明模型判断准确率提升，也不是接入原 App 的生产系统。

## 90 秒版本

> 反诈线索经常分散在聊天文字、截图、录音和短视频里。这个原型先在本机接收文字或一个媒体文件，为 OCR、二维码、语音转写等观察生成 `ev_001` 这样的证据编号，并对手机号、证件号、邮箱等做规则脱敏。随后确定性规则标出屏幕共享、验证码、安全账户等风险提示；RAG 从少量经过核对的知识卡中做 BM25 检索，也可以在本地 BGE 权重可用时加向量召回，再用 RRF 合并排名。
>
> 这些前置步骤不需要 Agent。Agent 用在调查路径会依赖新观察的部分：比如先检索，看到线索中的网址没有可信信誉源，就把结果记录成 `UNKNOWN`，再决定是否补问。出现疑似转账或远程控制线索时，它也能调用带官方出处的分场景止损指引，整理联系银行、报警前要准备的信息，检索本机历史相关视频，或将不确定案件升级到人工复核队列。LangGraph 循环受白名单、案件证据、去重和每轮最多 8 次调用约束。案件状态用 SQLite Checkpoint 保存。最后报告列出风险提示、证据、工具回执和限制。
>
> 现在它是本机原型。原有 Flutter、React、Spring 代码仍在仓库，但新增工作台没有接回那条调用链；RAG 语料和评测规模也不足以证明准确率或 Agent 收益。

这是在既有竞赛项目源码基础上的后续改造，不应把仓库里所有客户端和后端都说成自己从零开发。当前有两条并列路径：

## 从输入到报告：走一遍真实流程

1. **接收线索。** 首页既能输入文字，也能提交一个图片、音频或视频文件。演示按钮会创建固定的合成文本案件；不是预录轨迹。
2. **本地建立案件。** `jinjing/cases.py` 生成 UUID 案件目录，把来源媒体和 `manifest.json` 放在本机。上传大小上限在 Web 入口设为 50 MB。
3. **提取可用观察。** 图片处理 OCR 与二维码；视频按约 5 秒间隔抽样，最多 40 帧，并限制在 10 分钟内；音频和视频可调用本地 faster-whisper。缺少 ASR 权重时会标为不可用。
4. **做隐私替换和预览。** 手机号、身份证号、邮箱、银行卡长数字和带上下文的验证码替换成稳定占位符，如 `[PHONE_1]`。映射保存在本机 `private_tokens.json`，用于同一案件后续补充信息时保持占位符一致。图片预览会遮住被替换的 OCR 区域和检测到的人脸；原始上传媒体仍保存在本地案件目录。
5. **生成证据与规则结果。** 每条文本观察编号为 `ev_001` 等。规则对“安全账户转账”“屏幕共享并索要验证码”“刷单垫资”等组合给出风险等级和建议。规则命中是风险提示，不是最终诈骗定性。
6. **查知识和网址。** 初次建案时可以得到 RAG Top-3 资料和网址初检。Agent 后续也可再次调用知识检索。网址检查仅对本地维护的少数官方域名列表做匹配，不联网访问网页，也没有实时恶意网址库。
7. **Agent 调查。** Planner 读案件事实、风险级别、媒体类型、URL、已有决策、工具观察和剩余预算，提出一个结构化动作；执行层检查动作、调用工具、记录观察，然后返回 Planner。
8. **形成报告或补问。** 调查完成时保存 JSON 报告；需要用户补充事实时返回 `NEEDS_INPUT` 并显示问题。新事实会用同一案件的脱敏映射保存，再沿案件 Checkpoint 继续。补充事实后旧报告会标为过期，需重新调查。

## Agent 的关键设计：不是画一个循环图就算完成

### 感知、行动、观察

- **感知：** Agent 不直接看原始视频像素或整段原始录音。它接收前置流水线提取的文本事实、证据编号、规则级别、媒体信号、实际出现的 URL，以及之前的工具观察。
- **行动：** Planner 从当前允许动作中选一个。`Decision` 用 Pydantic 限定 `action/query/hypothesis/reason` 字段；工具可用性根据案件是否有 URL、是否含媒体动态决定。
- **观察：** 执行层写统一回执，包括工具、状态、签名、来源、来源版本、证据编号、时间、限制、错误码和耗时。观察加入状态后再交给下一轮 Planner。
- **循环终止：** Agent 选择 `FINISH`、请求补问、Planner 出错，或达到每轮最多 8 次工具调用时结束当前调查。LangGraph 递归上限随预算设置。

### 当前动作与工具

| 动作 | 做什么 | 边界 |
|---|---|---|
| `SEARCH_KNOWLEDGE` | 搜索本地已复核反诈知识卡 | 最多返回 3 条；无 BGE 权重时退化成 BM25。 |
| `CHECK_URL` | 对案件里真实出现的网址查本地官方域名登记表 | 不请求网站；未观察到的 URL 会拒绝；命中官方域名也不代表具体页面或发送人可信。 |
| `REVIEW_FORENSICS` | 读取已经产生的媒体来源、质量、音频和视频信号 | 它是对预处理结果的复核，不保证能鉴伪。 |
| `ASK_USER` | 证据不足时暂停并提出一个补充问题 | 属于人机交互动作，等待用户回复后才能继续。 |
| `BUILD_EVIDENCE_TIMELINE` | 按媒体时间戳整理 OCR、ASR 等线索；缺时间戳时按录入顺序列出 | 未标时间的内容不代表真实事件先后。 |
| `CHECK_EVIDENCE_GAPS` | 用关键词检查是否缺少转账状态、凭据披露、当前联系状态、独立核验等事实，并建议补问 | 只做缺口提示，不判断“没提到”就是“没有发生”；应结合上下文复核问题。 |
| `VERIFY_EVIDENCE_CHAIN` | 检查规则、知识卡和工具观察引用的证据 ID 能否对应已知记录 | 校验编号关联，不验证内容真实性。 |
| `GET_RESPONSE_PLAYBOOK` | 根据“仍在联系”“疑似已转账/凭据泄露”“设备可能远控”等场景，整理条件式止损步骤和出处 | 关键词命中不是事实确认；工具不会替用户冻结账户或报警。 |
| `PREPARE_REPORTING_CHECKLIST` | 汇总本案已有证据编号、网址主机和规则命中，并列出联系银行/报警前应准备的信息 | 不会发送数据或代为报案；用户应通过官方渠道提交原始材料。 |
| `FINISH` | 收敛并生成报告 | 不是一个外部工具。 |

首页现在展示 28 项能力：17 个自动处理、RAG、本地服务或经确认的外部适配组件，以及 11 个 Planner 可选动作（包括补问）。`FINISH` 是控制动作，不计入可选工具目录。面试时把目录数量与真实可调用动作区分开。

### 规划与模型差异

规划器支持本机 Qwen 0.5B 和 1.5B 模型。小模型路径只要求输出允许的动作名称，查询内容由代码根据案件事实构造；1.5B 路径尝试输出动作、查询、假设和理由的 JSON。两种都不是无限制自主执行：动作白名单和执行侧检查仍然生效。模型权重不随仓库提交。

代码中的 Planner 异常会转为 `NEEDS_REVIEW` 状态并停止调查；工具异常会转为 `ERROR` 观察，不直接泄漏异常文本。系统没有自动重试；Planner 读取错误后可以在剩余预算内改选其他动作，重复的“动作 + 参数”签名会被阻止。

### 记忆分三层来解释

1. **案件证据：** `local_cases/<case_id>/manifest.json` 保存脱敏观察、证据编号和处理状态。
2. **Agent 短期工作记忆：** LangGraph `SqliteSaver` 按 `case_id` 作为 `thread_id` 保存决策、观察、预算和当前状态。新事实可让同一案件从 Checkpoint 恢复，并开始新一轮工具预算；历史轨迹保留，同一轮里已执行的工具不能重复调用。
3. **Web Job 状态：** `QUEUED/RUNNING/DONE/ERROR` 和实时轨迹目前在 Python 进程的 `_jobs` 字典里；它不是 SQLite 持久队列，进程重启后可能丢失。

不要把案件 Checkpoint 说成用户长期画像、跨案件记忆或生产级任务恢复。

## RAG：面试官问“具体做了哪些”时

### 目前的检索链路

1. 知识卡先按 `SOURCE_VERIFIED` 状态和有效期筛选。当前 seed 知识库实际有 5 条人工核对资料，来源为政府/行业公开页面；每条保留标题、原始链接、发布时间和复核时间。
2. 对中文文本做 jieba 分词和 BM25 词项打分。
3. 反诈领域查询扩展表会补充同义或相关表达，例如“屏幕共享”扩到“共享屏幕、远程控制”，“安全账户”扩到“公检法、转账”。
4. 本地 BGE-small-zh 权重存在时，对查询和知识卡做向量编码；权重缺失时仅用 BM25，不阻塞演示。
5. 词法排名和向量排名用 Reciprocal Rank Fusion 合并，再给包含精确关键词的文档少量加权，返回 Top-3，并保留排名分数与来源字段。
6. 搜索观察通过 `evidence_id` 回链到知识卡，报告因此可以说明“引用了哪条资料”。这是一条可追溯检索链，不代表生成模型所有自然语言内容都有逐句事实校验。

### 被问到 RAG 八股时这样解释

- **为什么 BM25 + 向量：** BM25 对明确术语和短关键词稳定；向量召回能补充词面不同但语义相似的表达。融合能兼顾两边，但要用标注查询集测，不能凭感觉说“更准”。
- **为什么 RRF：** 不要求把 BM25 分数和余弦相似度校准到同一数值范围，按各自排名融合；当前实现用常见的 `1 / (k + rank)` 形式，`k=60`。
- **Chunk 怎么做：** 当前数据是少量人工整理的知识卡，没有实现大文档自动切片流水线。因此不要声称做了 parent-child、滑窗 chunk 或复杂 chunk 优化。
- **Metadata 有什么用：** 来源网址、发布时间、复核日期、区域、审核状态和有效期用于筛选与解释；过期或未核验资料不会进入检索集合。
- **重排做了什么：** 目前是 RRF 加精确关键词轻量加权，不是 Cross-Encoder，也没有独立 reranker 模型。
- **怎么评测：** 应建立人工标注查询和相关文档集合，分别报告 Recall@K、MRR、来源正确率、答案引用正确率和过期资料命中率。当前没有规模化检索评测结果。
- **幻觉怎么控：** 系统让 Planner 查询已复核卡片，回执保留来源，并对缺数据返回未知；这降低了无来源断言的机会，但不保证 LLM 绝不幻觉。面向公众还需要答案引用校验和人工抽查。
- **知识更新怎么做：** 当前通过 JSON 知识卡、审核状态和日期字段表达基本元数据；没有在线爬虫、自动审核、增量向量数据库或完整知识运维平台。

### 当前知识库的真实规模

可说：“现在是用 5 条权威/行业资料卡验证来源感知混合检索和降级路径，最近补了屏幕共享后止损和被骗后报警准备指引。语料规模和评测集还不足以比较检索效果。”不要说成“海量反诈知识库”。

## 多模态与 AIGC 识别：准确说出能力边界

| 输入或工具 | 当前做的事 | 不能推导的结论 |
|---|---|---|
| 截图/图片 | RapidOCR 提取文字；二维码识别；人脸框用于遮挡预览；保留 OCR 位置和置信度 | OCR 漏字或错字仍可能发生；人脸遮挡不是所有个人信息去标识。 |
| 视频 | 每 5 秒左右抽样，最多 40 帧；对抽样帧做 OCR/二维码与预览处理；检查文件技术质量 | 不是逐帧视频理解；没有证明覆盖剪辑、跨帧动作语义或所有攻击模式。 |
| 音频 | 可用本地 faster-whisper 转写；AASIST 可输出实验分数 | Whisper 权重缺失时不可用；AASIST 分数未对电话/社交视频场景校准，不能当伪造概率。 |
| 视频人脸信号 | DFDS 对抽样人脸帧输出实验分数 | 人脸裁剪流程与模型训练/推理设置不同，输出未校准，不能直接判定深伪。 |
| C2PA | 检查媒体是否有内容凭证及校验状态 | 没有凭证不等于伪造；有凭证也不等于内容真实或发布者可信。 |
| 文件质量 | ffprobe 查看时长、编码、分辨率、采样率等 | 技术质量只是判断证据是否足够的信号，不是内容真实性检测。 |

可以把项目说成“多模态线索处理与实验取证信号整合”，不要说“已经准确识别 AI 伪造视频/语音”。

## 隐私设计与限制

- 文本规则脱敏在本机执行，替换常见手机号、身份证号、邮箱、长数字账户和带标签验证码，并保留本地映射以便后续补问一致替换。
- Planner 的 query、hypothesis、reason 输出会再过已知 PII 模式检查；命中后进入 `NEEDS_REVIEW`。
- 图片生成本机模糊预览，OCR 命中区域会覆盖，人脸由 Haar cascade 检出后模糊。
- 案件媒体、manifest 和占位符映射保存在本地目录；“本地处理”不代表自动删除、加密存储或完全防止泄漏。
- 当前规则不能可靠识别人名、地址、声纹、背景信息、OCR 错字或语义推断出的身份；面向公网之前需要更完整的隐私评估、访问控制、保留期和删除策略。

## 如何回答“怎么证明它有效”

要区分三类证据：

1. **工程行为测试：** W6 记录在 2026-10-28 运行 21 项自动化测试全部通过，覆盖隐私替换、规则证据、检索来源、Agent 观察后改选、补问 Checkpoint、重复动作、工具失败和 Web 流程。它证明这些测试场景符合预期，不证明真实案件准确率。
2. **动作烟测：** W5 用 6 个手写场景比较固定第一步和小模型 Planner。报告中 0.5B、1.5B 都有 3/6 个场景选择了预设可接受动作，且有无效动作等失败样例。这只是小样本调试线索，不能说 Agent 提升了诈骗识别效果。
3. **缺少的效果评测：** 还需要独立盲测数据、人工标注、固定流程与 Agent 在同模型/同工具/同预算下对比，分别统计证据支持、正确补问与弃权、误报漏报、工具调用成本和耗时。RAG 也要单独测 Recall@K/MRR；深伪检测要按来源、压缩和内容域评估误报漏报。

如果问“现在能给一个准确率吗”，答：“没有足够代表性的标注集，所以我不会把 6 个研发场景当成准确率。现在能确认的是流程和边界测试通过；业务效果还需要专门评测。”

## 重点面试问答

### 1. 为什么不写普通代码工作流，要用 Agent？

> 我没有把全链路都 Agent 化。OCR、脱敏、规则和检索都是确定步骤，用普通代码做。Agent 用于调查分支：URL、媒体信号和检索结果会影响下一步；它可以检索本机相关视频、按风险建人工复核工单，也能给出条件式处置建议。固定工作流当然更简单、可预测；Agent 的价值假设是能根据新观察动态选择核验或补问。动作受工具白名单、每轮最多 8 次调用、重复动作阻断、失败观察和 Checkpoint 约束；外部 URL 扫描必须由用户确认。至于是否比同预算固定流程效果好，当前还没有足够评测证明。

### 2. Agent 循环具体在哪？

> `Investigator` 用 LangGraph 定义 `plan → execute → plan`，最后到 `report`。Planner 读案件状态和已有 observations 输出一个 `Decision`；执行节点调用工具，生成标准化 observation 并附上状态、来源、证据 ID、限制和耗时；下一轮 Planner 把最近观察纳入输入。选择补问或结束时转报告节点。

### 3. 它怎么防止工具乱调用？

> Planner 看到的动作是按案件条件过滤过的；执行层又会校验 URL 必须出现在案件里、动作必须在允许范围内、相同动作和参数不能重复，并限制工具调用次数。大多数工具只读，复核工单仅写本地队列；外部 URL 扫描需要用户单独确认，没有转账或发消息能力。模型提示只是一个约束层，真正的安全边界在代码执行检查。

### 4. 失败了怎么办？

> 工具异常被转换成带 `ERROR` 状态和错误类型的 observation，不把异常原文直接发到报告。Planner 可以读到错误后在剩余预算内选别的动作或结束；没有自动重试。Planner 自己格式错误或运行异常会停在 `NEEDS_REVIEW`，不会假装调查成功。

### 5. Checkpoint 算长期记忆吗？

> 不算。SQLite Checkpoint 按案件保存当前调查事实、决策、观察和预算，属于案件级短期工作记忆，支持补充事实后续跑。知识卡是 RAG 的领域知识，也不是用户记忆。Web Job 状态仍在内存，所以服务重启后任务状态可能丢失。

### 6. 为什么 BM25 和向量检索都要？

> 反诈查询里既有具体词，例如“屏幕共享、验证码”，也有表达不同但语义接近的说法。BM25 擅长显式词项，BGE 语义召回补充词面差异；RRF 按排名融合，不强行比较两种原始分数。当前 BGE 是可选依赖，缺失时退回 BM25。是否提升还要看标注集评测。

### 7. 为什么不用向量数据库？

> 现在只有 5 条知识卡，数据量和并发都不足以证明需要部署独立向量数据库。当前实现用本地模型算向量、进程内缓存知识卡向量，重点是来源筛选和检索链验证。语料规模扩大后，再按更新频率、过滤条件、并发和持久化需求选择 FAISS、pgvector 或专用服务，并做迁移评估。

### 8. 你们怎么保证回答有出处？

> 知识卡维护来源 URL、发布时间、复核时间、审核状态和有效期；检索结果保留这些字段并生成知识证据 ID，Agent 工具观察也记录引用 ID。它让检索依据可追溯，但目前没有逐句声明—证据自动校验，所以我不会说完全解决幻觉。

### 9. 深伪识别效果如何？

> 目前只集成来源凭证、文件质量和 AASIST/DFDS 的实验信号，模型分数没有在目标场景校准。报告把真实性状态保持为 `UNKNOWN`，实验分数不作为真伪结论。要做效果判断，需要覆盖真实语音、合成语音、压缩转码、不同设备和人脸裁剪的独立测试集，报告误报漏报和阈值选择。

### 10. 为什么说隐私优先？是不是保证隐私？

> 目前是本地处理优先：常见数字类 PII 先替换，媒体不上传云端模型，预览对部分 OCR 区域和人脸做遮挡，原始映射留在本地。但规则可能漏掉人名、地址和语义信息；数据也没有完整加密、生命周期删除和多用户权限。因此它是原型的隐私设计，不是隐私保证。

### 11. 这和原来的 App 如何集成？

> 当前没有把新 Agent 工作台接入原 Flutter/React/Spring 链路。仓库里有原系统的 Spring 到旧 Flask 模型 API 路径；新增 `local_web.py` 是 5050 独立本地入口。未来集成需要确定案件 API、身份权限、媒体存储、任务队列、状态同步和模型部署边界，不能只改一个 base URL。

### 12. 如果要上线你先做什么？

> 第一，先建立独立人工标注集，测规则、检索、Agent、媒体各自表现和不确定性；第二，把单进程内存任务队列换成可恢复的任务系统并做好权限、删除和审计；第三，补齐隐私威胁建模和数据保留策略；第四，对高风险结论加入人工复核和用户安全指引；最后才考虑在线 URL 情报源和生产部署。每个工具接入都要做来源、权限和失败语义审查。

### 13. 你个人做了什么？

准备一个真实版本，按照“我写/改了什么 → 为什么这么做 → 怎么验证 → 哪些仍未完成”。例如：

> 我参与了本地调查工作台的改造，具体负责的是【填写自己确实负责的功能/文件】。我遇到的问题是【真实问题】，于是选择【真实设计】；用【测试、浏览器流程、代码路径】验证了【具体行为】。还没有验证的是【真实限制】。

不要直接照读“我独立完成完整 Flutter + React + Spring + 大模型全链路”，除非确实如此并能提供证据。

### 14. 项目最难的工程问题是什么？

可讲工具错误和观察重规划，也可讲异步处理。回答时给出具体问题、改动、验证和剩余限制：

> 一个问题是工具失败以前容易被当成整段异常。现在把工具错误转成结构化 observation，让下一轮规划能看到工具名、失败状态和错误类型，再在剩余预算里选择替代动作或停止。测试验证了失败后动作改变。它目前没有重试策略，也没有证明在真实业务样本里会降低错误率。

另一个可讲故事：代码基线把 GAANet 接到“视频鉴诈”入口，但核对上游后发现它是音视频语音分离模型，并不支持深伪识别。改造时停止把它当伪造检测器，媒体能力改成来源凭证、质量和未校准实验信号，并在报告标为未知/不可用。这里展示的是核对模型任务并避免夸大能力。

### 15. 新增的业务工具具体帮用户做什么？

> 前一批工具偏证据整理。这一轮补了两个更贴近受害者处置的工具：一个按仍在联系、已转账/异常交易、设备可能被远控等情形，提供带官方出处的条件式止损建议；另一个把案件已有证据和联系银行/报警前要准备的交易信息整理成清单。它们不会代用户冻结账户、提交报案，也不会把关键词命中当成事实。

### 16. 如果用户已经转账，系统会怎么做？

> 系统会给出条件式的紧急处置提示：尽快通过银行或支付机构官方渠道联系并申请保护账户，尽快拨打 110 或联系公安机关，保留交易和通联记录；报案材料工具帮用户准备金额、时间、渠道、收款信息和证据线索。它不会承诺追回资金，也不能替代银行或警方的实时处置。

## 术语速查

| 术语 | 在本项目里的意思 |
|---|---|
| Agent | 一个有限预算、通过工具观察持续调整下一步的调查循环。 |
| Planner | 根据案件状态选择下一动作的本地 Qwen 规划器。 |
| Tool | Agent 能请求的只读调查动作，如检索和 URL 检查。 |
| Observation | 工具返回的结构化状态、来源、证据编号和限制。 |
| Checkpoint | LangGraph 用 SQLite 保存的案件调查状态快照。 |
| Working memory | 当前案件内的事实、计划和观察，不跨案件形成用户画像。 |
| RAG | 从经过筛选的外部知识卡检索资料，再把结果交给后续规划；本项目主要作为调查工具。 |
| BM25 | 基于词项频率和文档频率的关键词检索打分。 |
| Dense retrieval | 用 BGE embedding 比较查询与文档的语义向量相似度。 |
| RRF | 基于排名位置融合多个检索器结果的算法。 |
| `UNKNOWN` | 当前数据或工具不能给出可靠判断；不能解释成安全或伪造。 |

## 可以直接承认的不足

> 目前最欠缺的是独立评测和语料规模。现在的 21 项测试是工程行为测试，6 个场景是动作烟测，都不能替代真实案件的识诈效果评估。Agent 覆盖单案件和有限预算调查，视频检索仅限本机历史库，复核队列没有多用户权限；它有没有比固定工作流更好，需要同模型、同工具、同预算的任务级对照。工作台目前仅供本机演示，Web Job 内存状态、权限、数据保留和模型阈值都还没达到公共服务要求。

这段不是自我否定，而是准确说明当前证据，并给出下一步怎么验证。
